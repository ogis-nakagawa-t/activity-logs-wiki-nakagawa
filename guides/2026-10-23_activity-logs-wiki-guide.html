Windows の開発者モードを有効化する

.claude/skills/ の中身はシンボリックリンクです。Windows で一般ユーザーがシンボリックリンクを作るには、開発者モードが必要です。無効のまま clone すると、Git がリンクを通常のテキストファイルとして取り出し、Claude Code が .claude/skills/ からスキルを読めなくなります。リポジトリを clone する前に、次の設定を済ませてください。

  1. Windows の「設定」→「システム」→「開発者向け」で、開発者モードをオンにする。
  2. Git の core.symlinks がグローバル設定で true になっているかを確かめる。 
    git config --global --get core.symlinks

    true と表示されなければ（何も表示されない場合も含む）、次のコマンドで設定します。

    git config --global core.symlinks true
  3. clone した後、リンクとして取り出せたかを確かめる。LinkType が SymbolicLink と表示されれば成功です。 
    Get-ChildItem .claude/skills | Select-Object Name, LinkType

開発者モードを有効にする前に clone してしまった場合は、上の設定を済ませてから clone し直してください。

自分用リポジトリの作成

テンプレートリポジトリから自分用のリポジトリを作り、手元に取り出します。clone の前に、3 章の開発者モードと core.symlinks の設定を済ませておきます。

  1. テンプレートから作る。 GitHub で ogis-dac-rd/activity-logs-wiki-template を開き、「Use this template」から「Create a new repository」を選んで自分用のリポジトリを作ります。日報や工数を含むため、公開範囲は Private にします。
  2. サブモジュールごと取り出す。 スライド作成スキルを git サブモジュールで取り込んでいるため、--recurse-submodules を付けて clone します。
    git clone --recurse-submodules https://github.com/<自分のアカウント>/<リポジトリ名>.git

    付け忘れたときは、clone したフォルダで次を実行します。

    git submodule update --init --recursive
  3. 日本語のファイル名を正しく表示させる。
    git config core.quotepath false
  4. VS Code で開く。 推奨拡張の Foam（foam.foam-vscode）を入れると、ノート間の wikilink（[[10_Daily/2026/10/20]]）をたどれます。GitHub Copilot を使うときは、もう1つの推奨拡張 GitHub Copilot Chat（github.copilot-chat）も入れます。
  5. 個人設定を書く。 profile.md に担当領域、よく使う技術、記録の粒度、エージェントへの要望を書きます。既定の @[カテゴリ/プロジェクト名] もここに書けます。エージェントは作業を始める前に必ず profile.md を読みます。ただし、禁止事項とディレクトリの権限は profile.md では変えられません。リポジトリに含めたくない設定は CLAUDE.local.md（.gitignore 済み）に書きます。
  6. 週報に使う名前を書く。 profile.md の「自分の名前（週報に使用）」に自分の名前を書きます。週報テンプレート（templates/20_Weekly.md）の件名と本文の {自分の名前} に、この名前が入ります。

作ったリポジトリとテンプレートは Git の履歴を共有しません。テンプレートが更新されたときは、git merge ではなく専用の手順で取り込みます（11 章）。

Worktree を使わない設定

Claude のデスクトップアプリは、セッションごとに Git の worktree（作業用の別フォルダ）を作ることがあります。このリポジトリは日次ノートを1つの作業ツリーに書き足していく使い方なので、worktree を使わずに作業します。この設定は settings.json では指定できず、利用者がアプリ側で手動で設定します。

要確認デスクトップアプリで worktree を使わないようにする画面と項目名は、このガイドの作成時点で確認できていません。設定のしかたは説明会で画面を見ながら確認してください。

その他の設定（permissions と hooks）

よく使う安全なコマンドは確認なしで実行でき、削除や push のような戻しにくい操作は禁止されています。

区分対象
許可（確認なし）scripts/ の実行（powershell -NoProfile -ExecutionPolicy Bypass -File scripts/*）、Get-ChildItem、Test-Path、New-Item -ItemType Directory、Move-Item
許可（確認なし）git status / diff / log / add / commit / remote / fetch template / show / rev-parse、git submodule add / update / status
許可（確認なし）python .agents/skills/llm-wiki/scripts/check_evidence.py（wiki の根拠チェック）、python -I scripts/knowledge-graph-extend.py（ナレッジグラフの補完）
許可（確認なし）Bash の rm -rf 90_Wiki/.ua/intermediate（ナレッジグラフの中間ファイルの削除）
拒否PowerShell の削除系（Remove-Item、rm、del、erase、ri、rd、rmdir）、git push、git reset --hard
拒否Foam MCP の書き込み系（create_resource・update_resource・delete_resource・move_resource・add_tags・remove_tags・rename_tag）
拒否.env と .env.* の読み取り
フックWrite / Edit のたびに scripts/secret-scan.ps1 が書き込んだファイルを検査し、機密らしき文字列があればマスクを促す
フックBash / PowerShell を使う前に scripts/command-guard.ps1（Copilot と共通）が、削除系コマンド・git push・git reset --hard・.env の読み取りを拒否する。rm は rm -rf 90_Wiki/.ua/intermediate の形だけを通す。拒否ルールでは「この形だけは許す」という例外を書けないため、rm はフックで判定する
プラグインunderstand-anything（「ナレッジグラフを更新して」で使う）を project スコープで有効にしている。版は extraKnownMarketplaces の ref でタグ（v2.9.0）に固定している。すでに登録した PC は、固定先が上がっても自動では切り替わらないので、procedures/knowledge-graph.md の「プラグインの版を切り替える」の手順で登録し直す

.mcp.json の MCP サーバーのうち、settings.json の enabledMcpjsonServers に並べたもの（microsoft.docs.mcp・github・playwright・foam）は、確認なしで有効になります。

個人ごとの設定は .claude/settings.local.json に書きます。このファイルは .gitignore 済みです。

keep-steps-simple スキル

有効にすると、それ以降の応答が実行しやすい形に揃います。profile.md に「セッション開始時に keep-steps-simple を使う」と書いておくとエージェントが自分で有効にし、書いていなければセッションの最初に /keep-steps-simple と入力します。「normal mode」と伝えるまで有効です。

  • 1行目に、読み手がすぐ実行できる行動を置く
  • 複数の手順には番号を振り、1手順に1つの行動だけを書く
  • ターンをまたぐときは現在地を言い直し、所要時間は具体的に見積もる
  • 完了した成果は見える形で示し、最後に次の行動を1つ示す

テンプレートの profile.md には「セッション開始時に keep-steps-simple を使う」という要望の例が書かれています。

工数の集計

工数は、完了・中断を伝えるだけで自動的に計上されます。手で表を書く必要はありません。

  • 作業ログの開始時刻からの所要時間を 0.25h 単位に丸め、「⏱ 工数」表に記入する。同じタスクの行があれば加算する
  • 「工数は1.5h」のように指定すれば、その値が優先される
  • 「定例会議の工数を1hに直して」「開始時刻は9:00だった」と伝えれば修正される
  • プロジェクトコードは project-codes.md の対応表から引かれる。表に無い @[…] は空欄のまま記録され、「未登録」と報告される

対応表への行の追加は、工数システムの Excel からコピーした行（タブ区切りの6列）をそのまま貼り付けて頼めます。

プロジェクトコードを追加: TECH:研究開発	A295483100	ー	社内	【スキル】技術研鑽	【スキル】技術研鑽

キーを指定しないと、プロジェクト略称の【】内の語（上の例では「スキル」）がキーになります。既存のキーと重複するときは上書きされず、確認されます。

@[…] と project-codes.md の関係

@[カテゴリ/プロジェクト名] は工数を集計する単位で、ルートの project-codes.md は、その @[…] とプロジェクトコード（PJコード）を対応付ける表です。

  • @[…] の中身全体（/ を含むときは最後の / より後ろ。@[開発/クラウドデータ基盤] なら クラウドデータ基盤）を、表の1列目と完全一致で照らす。1列目にはこの照合キーを書き、/ は含めない
  • 一致した行の PJコードが「⏱ 工数」表のプロジェクトコード列に書かれる。週報の PJコード別集計では、その行のプロジェクト名称も使われる
  • 1つの PJコードに複数のキーを対応させてよい（例: クラウドデータ基盤 と DE勉強会 はどちらも A313271100）。週報の PJコード別集計では1つにまとまる
  • 一致しなければ推測でコードを書かず空欄にし、記録の報告に「未登録: @[…]」と添えられる。@[未分類] は常に空欄になる
  • 業務終了時に空欄をもう一度照合するので、日中に登録した分はそこで反映される。それでも未登録の @[…] は報告される
  • 週報では空欄の行を project-codes.md で補い、未登録のものは「（未登録）」として合計される

週報は作業ログではなく、上司が2〜3分で「何が進んだか・課題は何か・来週何をするか・相談したいことは何か」を把握するためのメールです。AGENTS.md の「週報の作成」に、次の書き方が決められています。

  • 会議への参加そのものは実績にせず、決定事項や合意事項を書く。細かな作業ログは入れない
  • 日次ノートなどの記録に無い成果や数値は推測で書かない。成果が判断できないときは「実施したこと」と「確認できたこと」を分ける
  • 課題には、できるだけ対応案を添える。課題や相談が無い節は省略してよい

スキルの自動更新（任意）

GitHub Actions を使う任意の設定です。.github/workflows/update-skills.yml が毎週月曜 9:00（日本時間）に動き、npx skills update でスキルを、git submodule update --remote でスライド作成スキルを最新にします。あわせて、understand-anything プラグインの版（.claude/settings.json の extraKnownMarketplaces の ref）を、取得元の最新のタグへ上げます。変更があれば自分のリポジトリへ自動でコミットします。一部のスキルは社内リポジトリ ogis-dac-rd/copilot-custom-hayashi から取得するため、その読み取りに使うトークン（PAT）を登録する必要があります。

PAT の設定

  1. GitHub の Settings → Developer settings → Personal access tokens → Fine-grained tokens で「Generate new token」を選ぶ。
  2. Resource owner を ogis-dac-rd にする。
  3. Repository access で ogis-dac-rd/copilot-custom-hayashi だけを選ぶ。
  4. Permissions で code（Contents）と Metadata を Read にする。
  5. 作ったトークンを、自分のリポジトリの Settings → Secrets and variables → Actions に、名前 SKILLS_TOKEN で登録する（ワークフローがこの名前で参照する）。
  6. Actions タブの「Update Agent Skills and Plugins」から「Run workflow」で手動実行し、成功するか確かめる。

要確認権限の項目名は、作成者のメモでは「code」です。GitHub の画面では「Contents」と表示されることがあるため、画面の表記で読み替えてください。組織の設定によっては、トークンの利用に組織管理者の承認が要る場合があります。

自動コミットは GitHub 上のリポジトリに入ります。手元に反映するには git pull を実行します。

プラグインをすでに登録した PC は、git pull で固定先の版が上がっても自動では切り替わりません。procedures/knowledge-graph.md の「プラグインの版を切り替える」の手順で登録し直します。

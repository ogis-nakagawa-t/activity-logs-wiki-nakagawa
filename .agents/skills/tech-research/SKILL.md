# 技術個別調査プレイブック

確定した調査対象の選択肢について、各選択肢の特性・根拠が明確な調査成果物を作成するために使います。
選択肢の列挙は [tech-options-pickup](../tech-options-pickup/SKILL.md) スキルで実施します。

## このスキルが扱う範囲

- 各選択肢の特性・制約・リスクの個別調査
- リスク、アンチパターン、情報鮮度の確認
- Web ページを一次情報源とした取得・検証・要約

## このスキルが扱わない範囲

- 調査対象の選択肢の列挙（[tech-options-pickup](../tech-options-pickup/SKILL.md) で実施）
- 選択肢同士の優劣比較・スコアリング・推奨案の作成
- 製品固有のデプロイ手順書
- 単一プラットフォーム向けの詳細 CLI コマンド集
- 明示的に求められていない実装レベルの詳細

意思決定後の実装詳細は、ドメイン固有スキルに引き継ぎます。

## 既定モード

- 明示がない限り、**完全非依存モード**で調査する
- 完全非依存モードでは、背景・目的・要件・制約を前提にしない
- 明示されたコンテキストがある場合のみ、依存セクションを追加する
- 依存情報が未提示でも、各選択肢の一般特性・一般リスク・一般制約は必ず記述する

## 利用する場面

次のような依頼に適用します。

- 各選択肢の特性・制約・リスクを個別に把握したい
- ステークホルダー向けの調査レポートを作りたい

## ワークフロー

前提: 調査対象の選択肢は [tech-options-pickup](../tech-options-pickup/SKILL.md) で列挙済みとする。

1. 調査モードを決める（既定: 完全非依存モード）
2. 各選択肢について必要な一次情報を取得する（URL 指定がある場合は全件を実取得）
3. 各選択肢の特性・制約・リスクを個別に記述する
4. コンテキストが明示されている場合のみ、前提・要件・制約・成功指標を追加で記述する
5. アクション項目と残リスクを含めて成果物化する

## 不明点の扱いルール（必須）

- 不明点は推測で補完しない
- 不明な事項は「不明」「非公開」「要確認」のいずれかで明示する
- 補完が必要な場合は、追加で確認すべき情報源（公式ドキュメント、一次情報 URL、ユーザー確認項目）を示す

## Web 情報源を使うときの調査ルール

### 基本原則

- URL 内容は推測せず、必ず実際に取得してから説明する
- ユーザーが URL を提示した場合は、最新状態の確認依頼として扱う
- 複数 URL がある場合は、全件を順に取得する
- 断定的な主張には出典 URL と取得日を添える

### 実行手順

調査目的（要約、検証、情報収集）を決め、重複を除いた対象 URL をすべて fetch で取得してから、主張・前提・制約・更新日を抽出する。同一選択肢の複数ソースで食い違いがないかを確認し、出典 URL と取得日を付けて結論を書く。不確実な点は、追加で確認する手段とあわせて明示する。

### 取得失敗時フォールバック

1. 同一 URL を再取得する（一時障害対策）
2. リダイレクト先や関連リンクを追跡する
3. 必要に応じて Browser 系ツールで取得する
4. 失敗が継続する場合は、理由と影響範囲を明示する

## 基本調査観点

各選択肢を個別に調査する際の観点として使い、案件に応じて調整します。
完全非依存モードでは「一般論として成立する範囲」で記述し、プロジェクト固有前提は混在させません。

- 機能適合性: 必須要件と推奨要件への適合度
- 非機能適合性: 性能、拡張性、信頼性
- セキュリティとガバナンス: アクセス制御、監査性、コンプライアンス
- 運用性: 導入容易性、監視、障害対応
- コストと TCO: 初期費用、固定費、運用負荷
- 相互運用性: 既存システムとの連携性
- チーム適合性: 学習コスト、必要スキル、運用責任分担
- 戦略リスク: ロックイン、ロードマップ不確実性、エコシステム成熟度

## 定量視点の導入（必須）

定性評価に加えて、次の定量値を記述します。

- **性能**: スループット（req/sec、MB/s）、レイテンシ（p50/p95/p99 ms）、同時接続数
- **コスト**: 月額 TCO 推定値、従量課金単価、初期費用（通貨・単位を明記）
- **規模の限界**: 公式に示されている最大値（ノード数、テーブル数、行数など）
- **SLA / 可用性**: 公式 SLA 数値（例: 99.9%）または「非公開」と明記
- **ライセンス**: 無償 / 有償、商用利用可否

定量値が公開されていない場合は「非公開」「要問い合わせ」と明記し、推測値を事実として記述しません。

## 成果物テンプレート

調査成果の詳細テンプレート（日付、調査者、具体例を含む）は [調査テンプレート](./references/research-template.md) を参照してください。

SKILL.md では、次の基本構成を最小限の骨組みとして示します：

- **必須（非依存）**: 各選択肢の特性・制約・リスク、情報鮮度
- **任意（依存）**: 調査の背景・目的、前提・制約、環境・規模・要件

## アンチパターン

次のミスを避けてください。

- 調査目的を固める前に実装論へ入る
- 調査を依頼されていないのに選択肢間の優劣を断定する
- Preview/Beta 機能を注意書きなしで安定機能として扱う
- URL を取得せずに一般知識だけで結論を出す
- URL リンク先の内容が古い可能性を考慮せずに結論化する
- URL の内容が不確実な場合に断定的な表現を使う
- 出典 URL や取得日を省略して根拠を曖昧にする
- ステータス 403/404/410/500 などの取得失敗をしたにもかかわらず、URL を記載する
- 不明点を推測で補完して記述する
- コンテキスト未指定なのに、特定環境の要件を前提に結論を固定する
- 定量値が取得できるのに「高速」「安価」などの定性表現だけで記述する
- 定量値が非公開・未測定の場合に推測値を確定値として記載する

## 情報鮮度の管理

調査結論は短期間で古くなるため、以下を必ず明記します。

- 根拠情報の日付（重要主張ごと）
- 想定製品バージョン
- 更新トリガー条件（例: メジャーリリース、価格改定、ポリシー変更）
- 見直し推奨頻度（例: 3-6 か月ごと）

## 推奨アウトプット形式

- 技術詳細版（フルレポート）
- 選択肢別調査シート（選択肢ごとの個別調査結果）

方法論は汎用形を維持し、プラットフォーム固有情報は「参考例」として扱います。

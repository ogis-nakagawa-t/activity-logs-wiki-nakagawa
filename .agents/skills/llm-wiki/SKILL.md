# LLM Wiki

LLM を使って個人のナレッジベースを作り、育てていく。扱うディレクトリは2つある。`80_Raw/`（変更しない一次資料）と `90_Wiki/`（まとめた知識の記事）だ。資料を 80_Raw/ に保存し、それを wiki の記事にまとめていく。wiki は時間とともに積み上がる。

Karpathy の考え方の中心は次の2つ。

- "The LLM writes and maintains the wiki; the human reads and asks questions."（wiki を書いて保守するのは LLM。人は読んで、問いを立てる）
- "The wiki is a persistent, compounding artifact."（wiki は残り続け、積み上がっていく成果物である）

このスキルはリポジトリの AGENTS.md の下で動く。AGENTS.md の実行環境・記録ルール・wiki ルール・禁止事項・Web コンテンツ取得ポリシーを常に守ること。

## 構成

次の3層は、すべてリポジトリのルートの下にある。

**80_Raw/**: 一次資料。読むだけで、変更しない。トピックごとのサブディレクトリにまとめる（例: `80_Raw/machine-learning/`）。

**90_Wiki/**: まとめた知識の記事。エージェントが責任を持って管理する。トピックのサブディレクトリは1段だけ（`90_Wiki/<topic>/<slug>.md`）。記事の図（SVG）は記事と同じディレクトリに `<slug>-fig-<n>.svg` として置く（下の「図」を参照）。特別なファイルが2つある。

- `90_Wiki/index.md`: 全体の索引。トピックごとに、記事1件を1行で書く（リンク・要約・更新日）。
- `90_Wiki/log.md`: 操作ログ。追記のみ。前の月までの記録は `90_Wiki/YYYY/MM.md`（月ごとのログ）にまとめる（下の「ログの月ごとのまとめ」）。`90_Wiki/YYYY/` はトピックのディレクトリではない。

**SKILL.md**（このファイル）: スキーマ層。構成と、すべての操作に共通する規則を定める。操作ごとの手順は `references/` の別ファイルにある（下の「操作」を参照）。

**情報源として使えるもの**: `80_Raw/` のほか、`10_Daily/`（日次ノート）と `40_Notes/`（調査・メモ）も記事の根拠にできる。ただし、この2つは後から追記・編集されることがある。外部資料（Web ページ、PDF、受け取ったファイルなど）は、必ず `80_Raw/` に保存してから使う。

書式の見本は、このファイルから見た `references/` にある。raw ファイル・記事・アーカイブページ・索引の正確な形式が必要なときに読むこと。操作の手順（`ingest.md`・`query.md`・`lint.md`）も同じディレクトリにある。

### メタデータ（frontmatter）

wiki の記事とアーカイブページには、AGENTS.md の wiki ルールに従って YAML frontmatter を付ける。Foam が特別に扱うキー（`type`・`title`・`tags`・`alias`）も、Foam の書式に合わせて書く。Foam 側の定義は `../foam-vscode/references/syntax.md` の「frontmatter」を参照すること。

```yaml
---
type: article # 記事は article、アーカイブページは archive
title: "記事のタイトル" # 本文の H1 と同じ
tags: ["wiki", "topic", "tag1", "tag2"] # 内容タグは任意個。アーカイブページは [wiki, archive, topic, ...]
alias: ["略称", "同義語"] # 任意。記事だけ
status: auto # auto | reviewed
sources: # 根拠ファイル。拡張子付きのルート相対パス
  - 80_Raw/topic/2026-10-20_example.md
  - 10_Daily/2026/10/20.md
credits: "Example Inc., 2026-10-01; 自分の作業記録, 2026-10-20" # 資料の著者・媒体と日付
updated: 2026-10-20 # 記事の知識内容を最後に変えた日
---
```

- `type` は Foam のグラフでの種類も兼ねる。raw ファイルは `raw`、記事は `article`、アーカイブページは `archive` にする。
- `title` は本文の H1 と同じ文字列にする。H1 を変えたら `title` も変える。
- `tags` は flow 形式（`[a, b, ...]`）で書く。先頭は raw ファイルなら `raw`、記事とアーカイブページなら `wiki`（アーカイブページは続けて `archive`）、続けてトピックのディレクトリ名を書き、その後ろに内容を表すタグ（技術名・概念・製品名など）を必要なだけ書く。内容タグの個数に上限はない。付ける前に既存のタグ（`foam list tags`）を確かめ、同じ意味のタグがあれば再利用して、表記ゆれを作らない。タグは英数字とハイフンだけを使う。キーワードは `"..."` で囲む。
- `alias` は記事の略称や同義語があるときだけ、flow 形式で書く。Foam のリンク補完に出る。raw ファイルとアーカイブページには書かない。キーワードは `"..."` で囲む。
- `title`・`tags`・`alias` だけを直したときは、`updated` を変えない（知識内容の変更ではないため）。
- `sources` は、拡張子付きのルート相対パスで書く。使ってよいのは `80_Raw/`・`10_Daily/`・`40_Notes/` の下のファイルだけ。
- `status` は、新規作成でも更新でも `auto` にする。`reviewed` にしてよいのは、ユーザーが確認したと言ったときだけ。内容を変えたら `auto` に戻す。
- アーカイブページは `type: archive` とし、`updated` の代わりに `archived` を書く。アーカイブページに `sources` は書かない。引用した wiki 記事は、本文の wikilink と「関連項目」で示す。
- `90_Wiki/index.md`・`90_Wiki/log.md`・月ごとのログ（`90_Wiki/YYYY/MM.md`）には frontmatter を付けない。

### 初期化

初めて Ingest するときだけ行う。`80_Raw/` と `90_Wiki/` があるかを確かめ、足りないものだけを作る。既存のファイルは上書きしない。

- `80_Raw/` ディレクトリ（`.gitkeep` 付き）
- `90_Wiki/` ディレクトリ
- `90_Wiki/index.md`: 見出しは `# ナレッジベース索引`、本文は空
- `90_Wiki/log.md`: 見出しは `# Wiki ログ`、本文は空

Query や Lint のときに wiki の構成が見つからなければ、自動では作らない。ユーザーに「先に資料を取り込んで、wiki を初期化してください」と伝える。

### ログの月ごとのまとめ

`90_Wiki/log.md` には今月の記録だけを置く。log.md に追記するときは、追記の前に次を行う。

1. 今日の年月を `scripts/now.ps1` の出力から取る。
2. log.md の記録（`## [YYYY-MM-DD] …` の見出しから、次の見出しの手前まで）のうち、見出しの年月が今月より前のものを探す。なければ、そのまま追記に進む。
3. 見つかった記録を年月ごとに分け、元の順のまま `90_Wiki/YYYY/MM.md` の末尾に移す（例: 2026-09 の記録 → `90_Wiki/2026/09.md`）。ファイルがなければ、見出し `# Wiki ログ YYYY-MM` で作る。`90_Wiki/YYYY/` ディレクトリがなければ作る。
4. 移した記録を log.md から取り除く。`# Wiki ログ` の見出しは残す。

- 記録の文言は変えずに移す。見出しの形は、機械が読み取るキーになるため。
- 月ごとのログも追記のみ。一度まとめた記録は直さない。
- 月ごとのログは記事ではない。索引に載せず、frontmatter・目次・図を付けない。
- トピックのディレクトリに、4桁の数字だけの名前を使わない（月ごとのログの置き場と区別するため）。

## 根拠の不変条件

wiki の記事が拠りどころにする事実（数値・日付・直接の引用）は、その記事の `sources` にあるファイルに、そのままの形で載っていなければならない。

- Compile のときに、この条件を**成り立たせる**。書く前に、その値が元資料のどこにあるかを確かめる。
- Lint のときに、この条件を**確かめる**。`scripts/check_evidence.py` が、目立つリテラルを元資料から探す。対象は、接尾辞付きの数値や大きな数値、小数、ISO 形式の日付、長めの引用。それ以外は、Compile のときの「書く前に確かめる」規則で守る。

80_Raw/ は変更しないので、一度確かめた記事はずっと確かなままだ。スクリプトは wiki 全体を数秒で検査し直せるので、差分の状態を管理する必要はない。10_Daily/ と 40_Notes/ は後から編集されうるので、Lint のたびに確かめ直す。

### 言語の扱い

- raw ファイルは、原文の言語のまま保存する。日本語で書くのは、スキルの文書と wiki の記事である。
- raw ファイルの `> [画像の読み取り]` ブロックでは、「図中の文字」を原文の言語のまま書く。「内容」欄（図の意味の説明）は日本語で書いてよい。
- 訳した文を「」・`""`・引用ブロックに入れてはいけない。引用してよいのは、原文そのままの文だけ。
- 数値は、元資料にある形のまま書く。42K は 42K と書き、4.2万 や 42,000 に直さない。
- 推測や補足は `> [Claude補足]` で区別し、裏付けのない記述は「仮説」と明記する（AGENTS.md の記録ルールと wiki ルールに従う）。

## 図（diagram-design）

記事やアーカイブページを作成・更新するときは、図にできる箇所（構造・流れ・関係・比較・時系列・数値）を探し、あれば `diagram-design` スキル（`../diagram-design/SKILL.md`）で SVG の図を作って入れる。どの型が合うかは、diagram-design の §2「When to Use」で決める。装飾だけの図や、箇条書きを箱に並べ替えただけの図は入れない。

この節の「記事への入れ方」「作り方」「図を直すとき」「Mermaid を使うとき」は、wiki 以外の資料（30_Projects/・40_Notes/）に図を入れるときにも使う（AGENTS.md の「図」）。そのときは「記事」を「その .md」、「記事の slug」を「その .md のファイル名（拡張子なし）」、「本文と `sources` にある事実」を「その .md の本文にある事実」と読み替える。根拠チェック（check_evidence.py）は 90_Wiki/ だけが対象である。

図は SVG を基本とし、Mermaid も使ってよい（下の「Mermaid を使うとき」）。

### 何を描くか

- 図に描くのは、その記事の本文と `sources` にある事実だけ。図にしかない事実を作らない。推測を描くときは、ラベルに「仮説」と付ける。
- 図の数値・日付は、本文と同じく「根拠の不変条件」の対象になる。元資料にある形のまま書く。
- ラベルは日本語で書いてよい。製品名やコマンドなどの固有の語は、元資料の表記のままにする。

### 記事への入れ方

図のファイルは、記事と同じディレクトリに `<記事の slug>-fig-<n>.svg` として置く（`n` は記事の中で 1 から振る番号）。記事からは標準の画像リンクで参照し、そのすぐ下に `> [図の説明]` ブロックを置く。.md の中に `<svg>` を直接書かない。

```markdown
![図: Ingest の流れ](llm-wiki-ingest-fig-1.svg)

> [図の説明]
> 種類: フローチャート
> 要素: 資料を受け取る、80_Raw に保存、振り分け、記事にまとめる、新規知見なし
> 関係: 資料を受け取る → 80_Raw に保存; 80_Raw に保存 → 振り分け; 振り分け → 記事にまとめる（新規・更新）; 振り分け → 新規知見なし（ログだけ）
> まとまり: 90_Wiki を変える: 記事にまとめる
> 強調: 振り分け（ここで扱いが決まるため）
> 要点: 資料は必ず保存し、記事にするかどうかは振り分けで決める。
```

- 画像リンクの代替テキストは `図: ` に続けて、SVG の `<title>` と同じ文字列にする。
- `> [図の説明]` は、図を見られないエージェントや人が、図の意味をたどるための文章である。正はこちらで、SVG はその描画とする。
  - **種類**: diagram-design の型の名前（フローチャート、アーキテクチャ、シーケンス、レイヤー、タイムラインなど）。
  - **要素**: 図のノード（箱）の名前を全部。
  - **関係**: 矢印や線を `A → B（ラベル）` の形で全部。`;` で区切る。双方向は `A ↔ B`、点線（任意・非同期）は `A ⇢ B` と書く。
  - **まとまり**: 枠やレーンで囲んだグループと、その中の要素。なければ行ごと省く。
  - **強調**: アクセント色で強調した要素と、その理由。なければ行ごと省く。
  - **要点**: 図が伝えることを1文で。
  - 数値の図（棒グラフなど）では、「関係」の代わりに **値** の行を書き、`項目: 値` を全部並べる。
- SVG に描いた文字（ノード名・矢印ラベル・凡例・数値）は、すべて `> [図の説明]` にも書く。`> [図の説明]` にない文字を図に描かない。例外は、diagram-design がノードに付ける種類タグ（`STEP`・`API` など）と見出しの小さなラベル（eyebrow）で、これらは書かなくてよい。
- `> [図の説明]` は原文の引用ではないので、引用の扱い（原文そのまま）を受けない。ただし中の数値・日付は、根拠チェックの対象になる。
- SVG の中には、diagram-design の規約どおり `<title>`（図の短い名前）と `<desc>`（内容を1文で）を入れる。

### 作り方

diagram-design の SKILL.md と、選んだ型の参照ファイル（`references/type-*.md`）を読んでから描く。そのうえで、wiki では次のように diagram-design の手順を決めておく。対話で止まらないようにするためだ。

- **スタイル**: リポジトリのルートに有効な `.diagram-design` マーカーがなければ、diagram-design §0 の質問はせず、「(e) 既定のまま」を選んだものとして進める。
- **フォント**: システムフォント（style-guide.md の「Font source」の `system`）にする。Google Fonts の `<link>` は入れない。日本語が OS のフォントで表示され、プレビューで外部と通信しない。
- **描く前の確認**（§3）: ユーザーの返事を待たない。選んだ型とサイズは、作業の最後の1行報告に含める。
- **固定の設定**: 明るい最小構成（`assets/template.html`）、サイズは `doc-inline`、アニメーションなし。
- **書き出し**: diagram-design では SVG の書き出しは頼まれたときだけ行うが、wiki の図ではこの手順の一部として書き出す。

手順:

1. `$env:TEMP` の下に、図ごとに新しい空ディレクトリを作る（例: `$env:TEMP/llm-wiki-fig-<YYYYMMDD-HHmmss>`）。リポジトリの中には作らない。
2. そのディレクトリに、`assets/template.html` を元に図の HTML を Write ツールで作る。HTML の名前は、最終的な SVG と同じ slug にする（例: `llm-wiki-ingest-fig-1.html`）。
3. diagram-design §9 のチェックリストを確かめ、次を実行して通るまで直す。
   ```powershell
   python .agents/skills/diagram-design/scripts/self_check.py --offline <HTML のパス>
   ```
4. SVG を書き出す。
   ```powershell
   python .agents/skills/diagram-design/scripts/export_svg.py <HTML のパス> <一時ディレクトリ>/<slug>.svg --system-fonts
   ```
5. 書き出した SVG を Read ツールで読み、その中身を Write ツールで記事と同じディレクトリ（例: `90_Wiki/<topic>/<slug>.svg`）に書く。スクリプトの出力先を直接リポジトリにしない（Windows では改行が CRLF になり、機密スキャンのフックも動かないため）。書いた後、改行をそろえて一時ディレクトリの SVG と同じ内容かを確かめる（写し間違いで座標や文字が変わっていないか）。
   ```powershell
   ((Get-Content -Raw <一時の SVG>) -replace "`r`n", "`n") -ceq (Get-Content -Raw <置いた SVG のパス>)
   ```
6. 記事に画像リンクと `> [図の説明]` を書く。
7. 一時ディレクトリのファイルは消さずに残す（削除は禁止）。HTML はリポジトリに入れない。

### 図を直すとき

- 図の元の HTML は残さない。図を直すときは、記事の本文と `> [図の説明]` から上の手順で描き直し、同じ名前の SVG を Write で上書きする。
- 図と `> [図の説明]` は必ず一緒に直す。片方だけを変えない。
- 図が要らなくなったら、記事から画像リンクと `> [図の説明]` を外し、SVG を `99_Archive/` へ `Move-Item` で移す。
- アーカイブページの図は、ある時点の写しなので直さない。

### Mermaid を使うとき

Mermaid（` ```mermaid ` のコードブロック）は、簡単なフロー・シーケンス・状態遷移など、Mermaid で十分に描けて、後から手早く直したい図に向く。diagram-design の型やスタイルが要る図は SVG にする。

- コードブロックのすぐ下に、SVG と同じ書き方の `> [図の説明]` を置く。Mermaid に描いた文字（ノード名・矢印ラベル・数値）は、すべて `> [図の説明]` にも書く。
- check_evidence.py はコードブロックの中を読まない。Mermaid の数値・日付は、`> [図の説明]` を通して根拠チェックを受ける。説明を省かないこと。
- SVG ファイルは作らない。図の点検（ファイル・`<title>`/`<desc>` の有無）の対象にもならない。
- 図を直すときは、コードブロックと `> [図の説明]` を一緒に直す。

## 操作

このスキルの操作は3つある。操作を始める前に、該当するファイルを必ず読み、その手順に従う。どの操作でも、このファイルの共通規則（構成・メタデータ・根拠の不変条件・図・規約）を守る。

| 操作                | トリガーの例                                                                               | 手順のファイル         |
| ------------------- | ------------------------------------------------------------------------------------------ | ---------------------- |
| Ingest（取り込み）  | 「wikiに追加: <URL/パス>」「<資料>をwikiに取り込んで」「このテーマを調べて wiki に入れて」 | `references/ingest.md` |
| Query（問い合わせ） | 「wikiで調べて」「<X> について何を知っている？」、答えを wiki に保存する（アーカイブ）     | `references/query.md`  |
| Lint（点検）        | 「wikiを点検」                                                                             | `references/lint.md`   |

## 規約

- 標準的な Markdown を使う。wiki 内のリンクは Foam のパス付き wikilink（`[[90_Wiki/topic/slug]]`）、frontmatter の `sources` は拡張子付きのルート相対パスで書く。会話中の出力では、ルート相対パスの Markdown リンク（例: `[タイトル](90_Wiki/topic/slug.md)`）を使う。
- 90_Wiki/ のトピックのサブディレクトリは1段だけ。それより深くしない。
- ログ・収集日・アーカイブ日には、今日の日付を使う。日付は `scripts/now.ps1` の出力から取る。`updated` は記事の知識内容が最後に変わった日。公開日は資料から取る（分からなければ `不明`）。
- Ingest では `90_Wiki/index.md` と `90_Wiki/log.md` の両方を更新する（新規知見なしのときはログだけ）。アーカイブ（Query から）でも両方を更新する。Lint では `90_Wiki/log.md` を更新する（索引の行を自動で直したときだけ `90_Wiki/index.md` も更新する）。ふつうの Query ではファイルを書かない。`90_Wiki/log.md` に追記する前には、必ず「ログの月ごとのまとめ」を行う。
- ファイルは UTF-8（BOM なし）、改行は LF。作成・編集には Write/Edit ツールを使う。シェルのリダイレクトでは書かない。図の SVG も同じで、スクリプトの出力を Read してから Write で置く。
- ファイル名の slug は英数字とハイフンだけ（日本語や空白は使わない）。図は `<記事の slug>-fig-<n>.svg` にする。
- ファイルは削除しない。不要になったものは `99_Archive/` へ `Move-Item` で移す。80_Raw/ のファイルは編集も移動もしない（例外は下の機密マスクだけ）。`> [画像の読み取り]` ブロックは保存のときにだけ書き、後から足したり直したりしない。
- 機密情報は、Write/Edit のたびに PostToolUse フックとして動く `scripts/secret-scan.ps1` が検出する。フックが検出を報告したら、該当する部分を `***` に置き換え、ユーザーに知らせる。80_Raw/ のファイルでも同じように置き換える。80_Raw/ で許される編集はこれだけ。マスクした値は raw と wiki の両方で `***` になるので、根拠の不変条件は崩れない。
- 記録のたびに、何をどこに書いたかを1行で報告する。
